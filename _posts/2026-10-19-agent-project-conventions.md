我给 Claude Code、Codex 这类编程代理写了一份跨项目通用的规范，想让它们在哪个仓库里都按同一套规矩干活：先查仓库事实再动手，结论标明依据，只改需求要求的代码，交付前自己 review 两轮。

这些规则原本每个项目都要写一遍，分散在各个仓库里，改了这边忘了那边，几份说法慢慢就对不上了。所以我把它们拆成一个文件，项目的 `CLAUDE.md` 或 `AGENTS.md` 用一行引用，项目文件里只写这个项目才有的东西：产品定位、模块边界、不能破坏的业务不变量、命令入口，还有依赖台账放在哪。两边冲突时听项目文件的，用户当前的要求又高于两者。

# 通用项目规范

本文件是跨项目通用的开发代理规范，不含任何具体项目的业务信息。

引用方式：在项目的 `CLAUDE.md` / `AGENTS.md` 里写一行 `@/path/to/project-conventions.md`，再在项目文件中补充本项目特有的内容：产品定位、模块边界、不得破坏的业务不变量、命令入口、依赖台账位置。项目文件与本文件冲突时，以项目文件为准；用户当前要求优先于两者。

## 1. 事实来源与冲突处理

- 判断已实现现状，以可运行代码、配置和测试为准；判断目标行为，以产品、架构文档或 ADR 为准。设计文档里尚未落地的目录和组件，不能当作现状。
- 发现文档与代码冲突时，不要自己拼一个结论：指出冲突，确认哪边是权威来源，并在同一次改动中修正文档。
- 仓库根目录有 `.codegraph/` 时，理解或定位代码先用 CodeGraph，再用文本搜索。

## 2. 认知诚实

技术判断以证据为准，不迎合。被质疑时先看有没有新事实；没有新证据就不为了表面一致改结论。发现原判断错了，直接说明错在哪、依据是什么。

非平凡的结论标明依据：

- `[已验证]`：读过对应代码、配置或文档，或实际运行过命令并检查了输出。静态检查通过不等于功能已验证。
- `[推断]`：从已确认事实推导，没有实际运行验证。
- `[常识]`：语言、协议或工程领域的稳定知识。
- `[记忆]`：来自已有知识，没有在当前仓库或权威资料中复核。易变或高风险的事项不能停在这一层。
- `[猜测]`：没有依据。默认不输出，必须提及时明确标注。

置信度用 `HIGH`、`MED`、`LOW`、`VERY LOW`、`UNKNOWN`，不用精确百分比。不知道就说需要验证；不得编造 API、路径、版本、提交、错误码、性能数字或测试结果。

## 3. 核心工程原则

- **架构与领域优先**：计划阶段以理想架构为目标，先明确业务目标、领域边界、模块职责、依赖方向和数据流，再编码；不为短期便利牺牲整体设计。设计要完整，实现要克制：不做推测性抽象，第二个真实用例出现前，单一场景直接实现。
- **模块优雅**：高内聚、低耦合，用精简稳定的接口封装内部复杂度。单个代码文件不超过 500 行，函数或方法不超过 50 行；接近上限先按职责重构模块边界，不能靠压缩格式或合并语句绕过。存量超限文件不再增长，下次实质改动时先拆分。
- **边界与数据流清晰**：协议模型、领域模型、持久化模型和视图模型互不泄漏；数据在边界处完成校验和转换，不跨层共享可变状态。模块不直接读写其他模块的内部状态；没有第二种实现或测试替身时，不额外抽象接口。
- **安全与隔离默认开启**：按多租户、多用户设计，明确认证、授权和数据隔离边界；最小权限；外部输入一律不可信。密钥、支付信息、Cookie、请求正文等敏感数据不进入代码、日志、Trace、错误信息、审计记录或响应。
- **面向并发与故障**：后端主动考虑幂等、竞态、事务边界、超时、取消、重试、背压和资源释放；不用无边界重试、吞错或隐式共享状态掩盖问题。
- **完整前端体验**：控制渲染成本、异步状态和并发请求；用户流程覆盖加载、空状态、错误、重试、反馈和可访问性。
- **复用稳定的业务语义**：优先复用已有模块和能力，但不因代码外形相似就过早抽象。确需重复时，在契约文件里写明为什么独立演进。
- **依赖克制**：新增依赖前先核查已有依赖能否满足，先查文档和类型定义，不臆断已有库缺功能；确需引入时选成熟且维护良好的库，不重复实现通用功能，不复制许可证不兼容的源码。
- **为维护者保留上下文**：非显然的设计决策、兼容约束、已知缺陷和临时方案，记录原因、影响范围、潜在风险和移除条件，写进契约文件、ADR 或 commit message。技术债关联 Issue；不留缺少上下文的 TODO。
- **可验证、可观测、可回滚**：每项改动行为可测试、运行状态可观测、故障可定位，兼顾向后兼容和回滚路径；错误与日志保留诊断上下文，但不泄露敏感信息。
- **删除优于兼容**：内部重构直接删掉过时实现，不加兼容层、deprecated shim 或双写逻辑。对外契约（稳定 API、数据库迁移）的兼容性按协议单独评估，那是合同义务，不是迁就旧代码。

## 4. 工作规则

### 先想清楚再动手

- 先查仓库事实再设计或编码；未知信息写成待确认项，不编造。
- 把假设写出来。需求有多种理解时，列出各自做法请用户选；有更简单的做法直接提，该反驳就反驳。
- 疑点会改变方案方向时停下来问；其余细节按最保守的可行方案处理，并在交付说明里写明假设。

### 简单优先（KISS）

- 选择满足当前需求的最简单实现，不为假设中的未来需求预建服务、抽象层或扩展点。
- 函数和模块只承担一个清晰职责。代码难以命名、难以测试或要跨越多个业务边界时，先拆清职责，再考虑复用。
- 优先使用标准库、仓库已有能力或维护正常的成熟依赖，最后才自己写。
- 只写解决当前问题的最少代码：只做用户要的功能，只用一次的逻辑直接写，可配置项等真有第二种取值再加。200 行能缩到 50 行就重写。
- 编码前先检索已有实现，能引用或复用的不重复写。
- 错误处理放在真实会失败的地方（见第 5 节）。

### 外科式改动

- 只改完成任务必须改的代码，沿用所在文件的既有风格。检验标准：diff 里每一行都能追溯到本次需求。
- 顺带看到的无关问题、死代码和可改进之处写进交付说明，由用户决定。例外：改到的代码里残留的存量注释，顺手删除或上提到契约文件。
- 本次改动造成的孤儿（不再被引用的 import、变量、函数、样式、文案）同批删除。

### 目标驱动

- 动手前把任务写成可验证的完成标准：修 bug 先写复现它的失败测试再改到通过；加校验先写非法输入的测试；重构前后同一组测试都通过。无法自动化时，写明手工验证步骤和预期结果。
- 多步任务先列简短计划，每步附验证方式（`步骤 → 验证：检查什么`），上一步验证通过再往下走。完成以实际跑过验证为准。
- 变更行为时同步测试和权威文档。资金、安全、协议、异步一致性和数据迁移必须覆盖失败、重试、重复、取消和恢复路径。

### 偷懒阶梯（[ponytail](https://github.com/DietrichGebert/ponytail)）

先读懂问题、追完完整调用链，再按下面的顺序找解法，停在第一个成立的台阶：

1. 这东西真的需要吗？只是推测出来的需求就不做，并用一句话说明。
2. 仓库里已经有了吗？已有的 helper、类型或模式直接复用。
3. 标准库能做吗？
4. 平台原生能力能覆盖吗？比如用原生表单控件代替组件库，用 CSS 代替 JS，用数据库约束代替应用代码。
5. 已安装的依赖能解决吗？几行代码能写完的，不为它引入新依赖。
6. 能写成一行吗？
7. 都不行，再写能工作的最少代码。

- 修 bug 要修根因：改之前先找出被改函数的所有调用方，在共享函数里修一次，不要逐个调用方打补丁。
- 有意偷工减料、且已知上限的简化（全局锁、O(n²) 扫描、朴素启发式），按第 6 节记录上限和升级路径（契约文件或 commit message）。
- 不能简化掉的：信任边界的输入校验、防止数据丢失的错误处理、安全措施、可访问性基础、用户明确要求的部分。
- 有分支、循环、解析、资金或安全逻辑的非平凡代码，至少留一个可运行的检查，逻辑坏了它就会失败。
- 输出先给代码，再用最多三行说明：跳过了什么、什么时候再加。

## 5. 鲁棒性

实现时假定入参可能非法、网络会中断、上游会超时、异步消息可能重复或乱序、进程可能在任意步骤退出。

防御放在信任边界和真实故障点：外部输入、跨网络与跨进程调用、存储和消息投递。类型系统、构造函数或同模块调用方已保证的不变量不重复校验，不为不可能的情形写兜底分支。

- 显式处理错误，保留错误链和必要上下文；禁止静默吞错、按错误字符串分支、把失败伪装成成功。
- 跨网络、跨进程、跨协程的操作都传递取消信号并设置合理超时。重试区分幂等性，限定次数，避免放大上游故障。
- 校验外部输入、类型转换、集合边界、可空值和状态前置条件；请求路径和消息消费者不得因外部数据导致进程崩溃。
- 每个协程、连接、事务、锁、定时器和文件句柄都有明确的结束或释放路径。共享可变状态要有说得清的同步策略，并用竞争检测或等价手段验证。
- 数据库是业务事实源；缓存只存可重建状态；至少一次投递的消息消费者必须幂等。
- 无法安全降级时明确失败，不静默替换用户可见的对象或结果，不跳过鉴权，不绕过资金类不变量。

## 6. 注释规范：契约文件之外零注释

每个包或模块只有一个契约文件允许写注释，其余文件（含测试）零注释，语义靠命名、结构和类型承载。

- Go：每个包一个 `doc.go`，内容只有包文档注释加 `package xxx`。首句以 `Package <包名>` 开头。
- TypeScript：以目录为模块单位，每个模块目录一个 `doc.ts`，内容只有一段带 `@packageDocumentation` 的注释加 `export {}`。框架约定的顶层单文件契约写进上级 `doc.ts`。tsconfig 要包含它，未引用模块的 lint 规则要放行 `**/doc.ts`。
- 其他语言按同样取向：选定一个模块级契约文件，其余零注释。
- 新建包或模块时，契约文件与第一个实现文件同批提交；契约变了契约文件同批改。对不上的契约文件比没有更糟。

**契约文件写什么**：只写代码表达不了、调用方不知道就会用错的东西——职责一句话；入口和调用顺序；资源所有权（谁关闭、返回值能否跨调用持有）；终止语义与哨兵错误；并发约束；事务与幂等边界；构建标签导致的能力差异。前端另写：数据来源与请求契约、状态归属与失效、副作用的开启与清理、权限依赖、业务不变量。

**不写什么**：不复述签名和 props；不放选型论证、性能数字、历史踩坑。

**“为什么”的去处**：一次性决策理由进 commit message；长期约束进 `docs/adr/`；架构级不变量进设计文档；配置项含义写在入库的配置模板里（配置文件、样式文件、文案数据可正常注释）。

**用代码替代注释**：命名承载意图；需要解释的逻辑提取成名字能说清的函数或 Hook；JSX 分区注释改成命名子组件；解释性常量替代魔法值；用类型（字面量联合、可辨识联合、branded type、`never` 穷尽检查）让非法状态不可表达；外部数据用 `unknown` 加显式收窄，不用 `any`。

**例外**：编译器和工具链指令（`//go:build`、`//go:embed`、`//go:generate`、cgo preamble、`'use client'`）不算注释。`@ts-expect-error`、`eslint-disable-next-line <规则>`、`prettier-ignore` 视作技术债：写明具体规则、紧贴被抑制的行，禁止整文件关闭，理由进 commit message。生成代码不受约束，也不得手工编辑。

**反模式**：任何解释性注释（包括“临时的”）；被注释掉的代码；`TODO` / `FIXME`（未完成工作写进交付说明）；用注释兜底难懂的代码；把契约撒进实现文件，或在契约文件里堆签名和用法示例。

存量注释在触碰对应代码时顺手删除，属于契约的上提到契约文件；一次性全仓清扫须用户明确指示。

## 7. 开发工作流

### 先处理未知量

| 类别 | 处理方式 |
| --- | --- |
| 已知的已知 | 按已确认内容执行 |
| 已知的未知（答案会改变方案） | 实施前向用户确认 |
| 未知的已知（用户未明说的偏好） | 给出有实质差异的草案或原型供选 |
| 未知的未知 | 读相关代码、配置、测试、文档和历史决策，主动找失败路径 |

实施中遇到计划外情况，记录偏差（问题、处理方式、理由），继续完成仍然安全的部分；重大偏差或需要扩大权限、范围时停下确认。

### 六步执行

1. **复述需求与范围**：目标、验收结果、不做什么。验收写成可验证的标准；修 bug 的标准是一条先失败后通过的复现测试。列出边界和异常场景、待确认项。
2. **检查仓库事实并定方案**：读受影响模块、测试和权威文档；涉及长期边界查 ADR，涉及外部依赖查依赖台账和许可证。给一个推荐方案，确有不同取舍再补备选。接口、数据、兼容性和用户可见行为在编码前确认。
3. **实现并同步测试和文档**：最简单的可行实现；行为变化同步测试和权威文档；新增或升级依赖同步清单、锁文件和依赖台账。
4. **第一轮 Review（正确性、鲁棒性、安全）**：输入、状态和权限是否先校验；错误是否显式处理；超时、取消、释放路径；重试是否只用于可安全重试的操作；幂等、锁顺序、唯一约束、金额守恒；敏感信息是否泄露；失败、重复、乱序、取消、退出、恢复是否有明确结果和测试。发现问题就修，不留作 TODO。
5. **第二轮 Review（可维护性、性能、一致性）**：diff 是否只含必需改动、孤儿已清；命名、职责、边界是否清楚，有无无需求的抽象；重复代码、魔法值、无依据默认值；热路径有无多余解析、复制、分配、锁竞争或外部调用；测试有没有靠放宽断言、跳过、删除来掩盖失败；文档、ADR、依赖台账、迁移、配置是否与实现一致。两轮都要读实际变更，不能合成一轮笼统检查。
6. **验证、提交与交付**：跑仓库实际提供的格式化、静态检查、构建和测试命令（以 Makefile、README、CI 为准，没有的入口如实说明，不虚构）。失败先判断是实现问题、环境问题还是已有问题。命令输出被 rtk 等工具压缩时，以退出码为准：rtk 下 `biome check` 失败也可能显示 No issues，交付前用 `rtk proxy <命令>` 确认。

### 交付说明

- 新增、修改和删除的文件；
- 实际运行的检查与结果，未运行项及原因；
- 两轮 Review 的发现和修复；
- 偏差记录，没有就写“无”；
- 兼容性或迁移影响，破坏性变更单独标明；
- 所作假设，以及顺带发现但未处理的问题。

权限、密钥、迁移、幂等和资金相关测试失败时，不得作为可上线结果交付。

## 8. 仓库操作

- 提交使用 Conventional Commit 格式，只包含本任务文件，不混入用户已有或无关改动；`git add` 按文件添加。
- 新建目录提交前用 `git ls-files <目录>` 自检：名为 `vendor` 等被 `.gitignore` 命中的目录，会被 `git add -A` 静默跳过。
- 不要在 Go 的 `cmd/<程序>` 目录下直接跑 `go build .`，生成的同名二进制容易被误提交；构建用 `go build -o` 输出到被忽略的目录，或用 `go build ./...` 只做编译检查。
- commit message、PR 描述和 Issue 里不得携带任何 AI 信息或署名：不加 `Co-Authored-By: Claude` 之类的尾注，不写「Generated with Claude Code」，也不提及由 AI 生成。这条优先于工具或系统默认附加的署名要求。
- 分支策略、是否直接推送主分支，以项目文件约定为准。
- 不发布；不执行破坏性 Git 操作（force-push、改写历史、删除远程分支等）。除非用户明确要求，不改写已推送的提交。

## 9. 文档写作

文档写给一起做事的同事，目标是看得懂、能评审、能照着实施。

- 先查代码、配置和已有文档再动笔；不编造需求、指标和性能数据。无法确认的写进「待确认项」，并写明影响。同一术语全文只用一个名字。
- 开头一两句说清要解决的问题和结论，先讲全局判断再展开细节。没有内容的章节直接删，不照模板凑数。
- 文风：不写「随着业务发展」一类开场，也不写「综上所述」一类收尾；空泛评价换成指标或可观察结果，营销词换成具体动词。没有来源的说法写成待验证假设；不写对话腔，不硬凑三点，不加无意义的加粗。技术判断落到事实上，例如「超时 3 秒，最多重试 2 次」。选型写清放弃了什么，以及什么变化会触发重选。
- 多角色流程、三方及以上的调用时序、状态迁移和表关系配 Mermaid 图，文字能说清的就不画。交付前检查语法，并核对图和正文是否一致。
- 事实、假设和待确认项分开写。方案对比要先给选择，再给依据和代价。

### 交付流程（Sepia + Humanizer-zh）

1. 动笔前确定 [Sepia](https://github.com/Nanako0129/sepia) 的路线：新文档用 `write`，改已有文档用 `refactor`。`refactor` 要先列完整问题清单，再逐项做最小改写。只有用户要求诊断或全文重写时，才用 `review` / `recreate`。
2. 写完初稿后核对需求覆盖、事实来源、术语和口径；再做一轮技术检查，看字段、类型、单位、示例、边界条件、异常分支和图文一致性。
3. 输出前按所选路线运行 Sepia，做专业文本检查和风格检查，修掉实际命中的 AI 写作痕迹。技术含义、数字、术语和约束一律不改，也不补写未经确认的事实。
4. 再运行 [Humanizer-zh](https://github.com/op7418/Humanizer-zh) 做最后一轮文字编辑，并按它的五项标准评分；低于 45/50 就继续改，改完重新检查。
5. 两项技能跑完后只做事实、链接、格式和语法校验。正文还要改的话，改完重新跑 Sepia 和 Humanizer-zh。任一技能不可用或没执行，文档就不算完成，也不能只在文末声称「已检查」。
